# 프로젝트 원칙

> 2026-11-06 · 결정이 애매할 때 이 순서대로 판단한다.

## 제품 원칙

1. **아이 안전이 먼저.** 위험할 수 있는 활동은 승인 없이 보여주지 않는다.
2. **틀린 정보를 확신하듯 보여주지 않는다.** 모르면 "확인 중", 추정이면 "예상"이라고 쓴다.
3. **부모의 시간을 아낀다.** 한 화면에서 판단하고, 신청은 바로가기 한 번.
4. **배우는 내용과 연결한다.** 모든 추천은 성취기준을 통해 "왜 이걸 추천하는지" 말할 수 있어야 한다.
5. **작게 시작해서 넓힌다.** 서울·경기, 초등, 학부모, 핵심 기관 10~20곳. 안정되면 확장.

## 기술 원칙

1. **서버를 만들지 않는다.** Supabase(DB·인증·API) + Edge Functions + 야간 배치로 충분한 동안은 별도 API 서버를 두지 않는다.
2. **무거운 일은 밤에.** 수집·AI 생성은 배치에서 미리 만들어 DB에 둔다. 앱은 읽기만.
3. **권한은 DB가 지킨다.** 앱 코드가 아니라 RLS로 "내 자녀만" 보이게 한다.
4. **필요한 만큼만 수집한다.** 학교는 자녀가 등록된 곳만, 기관은 정해진 목록만.
5. **실패는 격리하고 기록한다.** 한 기관·한 학교의 실패가 전체를 멈추지 않게 하고, `collect_runs`에 남긴다.
6. **같은 입력에 같은 결과.** 배치를 다시 돌려도 중복이 생기지 않는다(upsert).
7. **옮길 수 있게 둔다.** 프롬프트와 수집 규칙은 저장소 문서로 둔다(API 전환 대비). 앱의 데이터 접근은 repository 한 계층에 모은다(API 서버 전환 대비).
8. **테스트 먼저.** 새 로직은 실패하는 테스트부터. 수집기는 저장된 HTML 샘플로 테스트한다.

## 협업 원칙

- 기능 단위로 브랜치를 만들고, 작은 커밋을 자주 한다.
- 결정은 문서(`docs/`)에 남긴다. 말로만 정한 것은 정해지지 않은 것이다.
- 외부에 보이는 작업(예약 작업 생성, 배포)은 사용자 확인 후 한다.

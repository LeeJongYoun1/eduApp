# eduApp 설계 문서 (v1) — 확정

작성일: 2026-11-06 · 확정: 2026-11-06

## 1. 의도와 이유

학부모와 선생님이 **아이가 지금 학교에서 배우는 내용**에 맞는 책·활동·체험 프로그램을 한곳에서 찾게 한다.

가장 큰 불편: 박물관·과학관·청소년센터 프로그램을 **기관 홈페이지마다 하나씩 찾아봐야** 하는 것.
그다음 불편: 신청 시작/마감을 놓치는 것, 그리고 프로그램이 아이 학년·배우는 내용에 맞는지 판단하기 어려운 것.

## 2. 사용자

- **학부모**: "요즘 아이가 뭘 배우지? 주말·쉬는 날에 뭘 하면 좋을까?"
- **선생님**: "다음 단원 수업 준비, 현장학습·수업 자료 찾기"
- 같은 데이터를 쓰고 화면 관점만 다르다. 선생님은 학교별 교재·진도 정확도가 더 중요하다.
- **v1(시범 운영)은 학부모만.** 선생님 기능(반 선택, 학급 시간표, 진도 수정, 선생님 화면)은 다음 버전.

### 계정 구조 (v1)
- 로그인 필수 (알림 때문).
- 학부모 1명 → 자녀 여러 명. 자녀마다 학교·학년. 관심 프로그램·알림은 학부모 단위, 추천은 자녀 단위.
- 운영자(본인) 계정: 실험 승인 화면 접근.

## 3. 목표 / 비목표 / 실패 조건

### 목표 (v1)
1. **학교 기준 교육과정 정보**: 학교를 선택하면 학년·시기별 교과과정, 그 학교가 쓰는 교과서(출판사)와 단원을 보여준다.
2. **책·활동 추천**: 학년·단원에 맞는 책과 활동.
3. **체험 프로그램 통합**: 지역 복수 선택 → 핵심 기관 프로그램(진행 중/예정)을 학년·날짜·우리 학교 쉬는 날로 필터.
   - 프로그램마다 연결 단원 꼬리표와 이유
   - **가기 전에 읽으면 좋은 책 + 이유** (체험 내용·학년·단원을 연결해 1~2문장)
   - 관심 프로그램 **신청 시작/마감 알림**
4. **오늘의 질문**: 이번 주 진도에 맞춘 식탁 대화 질문 하루 1개(정답 대신 생각 힌트).
5. **집에서 하는 미니 실험·만들기**: 집 재료로 하는 교과 연계 활동.

### 비목표 (v1에서 안 함)
- 유아·중·고 (초등만. 이후 확장)
- 선생님 기능 (다음 버전)
- 공개 출시 (v1은 지인 대상 시범 운영)
- 서울·경기 외 지역
- 체험 후 기록/관심사 지도, 방학·재량휴업일 계획표 (다음 버전)
- 앱에서 직접 프로그램 신청/결제 (기관 페이지로 링크)
- 사용자가 누르는 순간 AI가 생성하는 실시간 기능

### 실패 조건 (동작해도 실패)
- 틀린 교과서·단원 정보를 확신하듯 보여주는 것 (확인 안 된 정보는 반드시 "확인 중" 표시)
- 이미 마감된 프로그램이나 지난 알림
- 아이에게 위험한 실험 (불·칼·화학약품 등) 추천

## 4. 제약

- **지역**: 서울·경기만. 안정되면 확장.
- **학교 수**: 서울·경기 초등 약 1,900곳(대략). 전체를 미리 수집하지 않는다.
- **학교별 교과서 공개 데이터 없음**: 각 학교 홈페이지 공지사항 첨부(hwp/pdf)로만 공개됨. 2022 개정으로 초3~6 수학·사회·과학·영어 등이 검정 교과서이고 학교마다 출판사가 다르다.
- **교과서 목록 자체**는 교육부 공공데이터(서명·출판사·사용학년)로 확보 가능.
- **학사일정·시간표**: 나이스 교육정보 개방 포털 Open API (인증키 필요).
- **체험 기관**: API가 없는 곳이 많아 기관별 페이지 수집 필요.
- **AI 처리는 Claude 예약 작업(구독 사용량)** 으로 한다. 실시간 생성 불가, 하루 처리량에 한도 있음.
- **약관**: 개인 구독을 다중 사용자 서비스의 자동 처리에 계속 쓰는 것은 정식 서비스 전 확인 필요. 정식 확장 시 Claude API로 옮길 수 있게 프롬프트·수집 규칙을 저장소에 문서로 둔다.
- **네트워크**: 예약 작업 환경의 네트워크 접근을 Full(또는 필요한 도메인 허용)로 바꿔야 수집 가능. 현재 개발 컨테이너에서는 해당 사이트 접속 불가 → 수집기는 저장된 샘플 페이지로 개발·테스트.

## 5. 접근 방식 (검토한 것)

| | 구성 | 장점 | 단점 |
|---|---|---|---|
| A. Firebase 중심 | Firestore + Cloud Functions | 로그인·푸시 한곳 | 학교→교과서→단원→프로그램→책 연결 조회가 불편 |
| **B. Supabase + 예약 배치 (선택)** | Postgres + 매일 배치 | 얽힌 데이터에 관계형 DB가 자연스러움, 서버 관리 없음 | Supabase + Firebase(푸시) 두 서비스 |
| C. 직접 서버 | Python 서버 + DB | 자유도 | 운영 부담 |

**선택: B 수정안** — 배치 실행을 GitHub Actions + Claude API 대신 **Claude 예약 작업**으로 해서 별도 API 비용을 없앤다.
학교 교과서 수집 방식은 A(학교 홈페이지 공지 자동 수집)를 선택했다. (사용자 직접 입력 / 정보공개청구 방식도 검토함.)

## 6. 결정된 구조

```
[Flutter 앱] ──읽기/쓰기──▶ [Supabase: Postgres + Auth]
     ▲                              ▲
     │ 푸시                         │ 결과 저장
  [FCM] ◀──알림 발송── [Claude 예약 작업: 매일 새벽 1회]
                         - 수집 대기 학교 처리
                         - 기관 프로그램 수집
                         - AI 생성(추출·연결·추천·질문·실험)
```

- **앱**: Flutter (안드로이드 우선).
- **DB/인증**: Supabase.
- **푸시**: FCM (Firebase Cloud Messaging).
- **배치**: Claude 예약 작업이 매일 1회 새 세션으로 실행. 수집 스크립트는 Python(hwp/pdf 처리 도구가 가장 풍부).

### FE / BE / DB 구분과 저장소 구조

| 구분 | 담당 | 하는 일 |
|---|---|---|
| FE | Flutter 앱 | 화면, 자녀·지역 선택, 알림 수신 |
| BE | Supabase 자동 API + RLS | 데이터 조회, 권한 확인 |
| BE | Edge Functions | 알림 발송, 운영자 승인, 학교 수집 요청 |
| BE | Claude 예약 작업 + Python 스크립트 | 수집, AI 생성 (야간 배치) |
| DB | Supabase Postgres | 학교, 교과서, 성취기준, 프로그램, 책, 사용자 |

```
eduApp/
├── app/              # FE: Flutter 앱
├── supabase/
│   ├── migrations/   # DB: 테이블, RLS
│   └── functions/    # BE: Edge Functions
├── batch/            # BE: 수집 스크립트, AI 프롬프트, 예약 작업 지침
└── docs/
```

- **인증**: Supabase Auth (JWT 발급). 자체 JWT 서버는 만들지 않는다 (아동 개인정보 보안 위험·개발량).
- **별도 API 서버(3계층) 없음**: 실시간 AI 처리, Supabase 이탈, 다중 클라이언트가 필요해질 때 도입. 대비책으로 Flutter 앱의 데이터 접근 코드를 한 계층(repository)에 모아, 그때 그 부분만 바꾼다.

### 학교 선택 → 교과서 수집 흐름
1. 사용자가 학교 선택 (나이스 학교 목록에서).
2. 미수집 학교면 **수집 대기 목록**에 추가.
3. 다음 배치에서 그 학교 홈페이지 공지에서 "교과용도서 선정 결과" 게시물·첨부를 찾아 과목별 출판사 추출.
4. 완료 시 사용자에게 푸시 "교과서 정보가 준비됐어요".
5. 기다리는 동안: 해당 학년 가장 많이 쓰는 출판사로 임시 표시 + "확인 중".
6. 못 찾음/애매함: 사용자가 출판사 직접 선택 (보조 수단).
7. 수집된 학교는 교과서 선정 공지 시기에 연 1회 재확인.
8. 실패한 건은 표시해 두고 다음 배치에서 재시도.

### 체험 프로그램
- 초기 대상: 서울·경기 **핵심 기관 10~20곳** (국립중앙박물관, 국립과천과학관, 지역 청소년수련관·문화센터 등). 공공 API(e청소년 청소년활동정보, 문화포털 등)가 있으면 우선 사용.
- 기관별 수집 규칙을 따로 둔다 (홈페이지 바뀌면 그 규칙만 수정).
- 알림: 관심 표시 프로그램에 대해 신청 시작 1일 전·1시간 전, 마감 임박. 신청 시작 시각이 불명확한 기관은 "신청 기간"만 안내.

### AI 생성물 (모두 배치에서 미리 생성해 DB 저장)
- 공지 첨부에서 과목별 출판사 추출
- 프로그램 ↔ 학년·단원 연결 + 이유
- 체험 전 읽을 책 + 이유
- 오늘의 질문 (학년·단원별로 미리 생성, 날짜별 배정)
- 집 미니 실험·만들기 (안전 기준 통과한 것만)

### 데이터 출처
| 데이터 | 출처 |
|---|---|
| 교육과정(학년·단원 성취기준) | 국가교육과정정보센터(NCIC) |
| 교과서 목록 | 교육부 교과서 관련 정보(공공데이터포털) |
| 학교별 교과서 | 각 학교 홈페이지 공지 첨부 |
| 학교 목록·학사일정·시간표 | 나이스 Open API |
| 책 | 교과서 수록 작품, 교과 연계 도서, 도서관 정보나루(학년대 인기 대출) |
| 체험 프로그램 | 기관 홈페이지 / 공공 API |

## 7. 설계자가 정한 것 (검토 후 추가, 사용자 확인 대상)

- **연결 기준은 성취기준**: 교과서 단원 목록은 출판사마다 달라 공개 데이터가 없다. 그래서 프로그램·책·질문·실험은 모두 **NCIC 성취기준**(출판사와 무관하게 공통)에 연결한다. 출판사별 단원명은 배치가 출판사 사이트에서 수집해 성취기준에 매핑하고, 수집된 경우에만 "우리 교과서 ○단원"으로 함께 보여준다.
- **이번 주 진도는 추정치**: 나이스 시간표는 과목만 주고 단원은 주지 않는다. 학사일정과 성취기준 순서로 진도를 추정하고, 화면에 "예상 진도"라고 표시한다. (진도 수정은 선생님 기능과 함께 다음 버전.)
- **교과서 출판사 수정은 학부모가**: 선생님 기능이 빠졌으므로 "확인 중"이거나 틀린 출판사는 학부모가 고친다.
- **시간 맞춘 알림은 배치와 분리**: "신청 1시간 전" 같은 알림은 하루 1회 배치로는 보낼 수 없다. 그래서 **Supabase 예약 기능(pg_cron) + Edge Function**이 DB의 알림 시각에 맞춰 FCM을 보낸다. 여기에는 AI를 쓰지 않는다. Claude 배치는 알림 시각을 DB에 기록만 한다.

## 8. 사용자가 정한 것 (2026-11-06)

- **AI 결과 검토**
  - 교과서 출판사: AI가 확신한 것만 바로 표시, 애매하면 "확인 중". 사람 검토 없음.
  - 집 실험·만들기: **운영자가 승인한 것만** 앱에 노출. 배치는 후보를 "승인 대기"로 저장하고, 운영자가 승인 화면에서 승인/거절.
- **운영 단계**: 시범 운영. Claude 예약 작업으로 처리하고, 공개 출시 때 Claude API로 옮긴다.
- **대상**: 학부모만 (선생님 기능 제외).

# 매일 수집 예약 작업 지침

Claude 예약 작업이 매일 새벽(KST) 새 세션에서 이 문서를 따른다.

## 전제
- 환경 네트워크 접근: Full
- 환경 변수 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`: 배치는 Supabase REST(HTTPS)로 저장한다 (이 클라우드 환경에서는 DB 직접 연결이 막혀 있음)
- 환경 변수 `NEIS_API_KEY`: 학교 단계(학사일정 수집)에서 쓴다
- `batch/work/`는 작업용 임시 폴더(git 제외). `pip install -q -e .`가 pypdf·olefile까지 설치한다

## 순서
1. `cd batch && pip install -q -e .`
2. `python -m eduapp_batch.run_programs`
3. 마지막 줄 JSON을 확인한다. 값이 숫자면 저장 건수, 문자열이면 그 기관의 오류.
4. 오류난 기관이 있으면: 해당 기관 페이지를 열어 구조가 바뀌었는지 확인하고, 원인을 한 줄로 기록한다. 이 세션에서 코드를 고치지 않는다(사람 확인 후 수정).
5. 프로그램 결과 요약(기관별 건수, 실패 기관과 원인)을 남기고 학교 단계로 간다.

## 학교 단계 (교과서 출판사)
6. `python -m eduapp_batch.run_schools prepare` — 자녀가 있는 학교의 학사일정을 저장하고, 수집 대기·실패·오래된 학교의 공지를 읽어 `work/<neis_code>/`에 `text_<n>.txt`(첫 줄 `# <게시물 제목> | <첨부 이름>`, 게시물 본문은 이름이 `(본문)`)와 `meta.json`을 쓴다. 한 번에 최대 20개 학교만 처리하고 나머지는 다음 실행이 이어받는다.
7. `text_*.txt`가 있는 `work/<neis_code>/` 폴더마다(`work/_done/`은 건너뛴다) 글과 `meta.json`을 읽고 같은 폴더에 `answer.json`을 쓴다. prepare는 글을 새로 쓴 학교의 이전 `answer.json`을 지우므로, `text_*.txt`가 있는 학교마다 항상 `answer.json`을 새로 쓴다. 모양은 정확히 이렇다 (찾은 게 없으면 `items`는 빈 목록). `grade`는 정수, `certain`은 문자열이 아닌 JSON 불리언이며 둘 다 필수다. 아니면 apply가 그 파일 전체를 거부한다:
   `{"items": [{"grade": 4, "subject": "과학", "publisher": "천재교육", "certain": true}]}`
8. `python -m eduapp_batch.run_schools apply` — `answer.json`이 있는 폴더만 처리한다. `certain: true` 항목을 저장하고, 처리한 폴더는 `work/_done/`으로 옮긴다.
9. 두 명령 모두 마지막 줄 JSON을 확인한다(`{"<neis_code>": 값}`; 전체 실패면 `{"error": ...}`).
   - prepare: 숫자 = 쓴 글자 파일 수. 문자열 = 사유. `홈페이지 주소 없음`·`지원하지 않는 홈페이지`·`교과서 선정 공지 없음`·`첨부에서 글자를 읽지 못함`은 not_found로 기록되고, 그 밖의 `예외이름: 메시지`는 실패(failed)로 기록되어 다음 실행에서 자동 재시도된다. not_found로 끝난 학교는 자동 재시도되지 않는다.
   - apply: 숫자 = 저장한 항목 수(0이면 not_found, `답안에 확신하는 출판사 없음`으로 기록). 기대보다 적으면 DB가 항목을 거부했을 수 있다. 항목별 거부 사유는 출력 JSON에 없고 실행 기록(`collect_runs`)에만 남는다. 문자열 = `answer.json` 형식 오류 등 오류이며 폴더는 그대로 남는다.
10. 같은 학교가 반복해서 실패할 때만 사람 확인이 필요하다고 요약에 적는다. 코드는 고치지 않는다.
11. 학교별 결과(저장 건수, not_found·실패 사유)를 한 문단으로 요약하고 진도 단계로 간다.

### answer.json 작성 규칙
- 과목은 `수학`·`사회`·`과학`·`영어`만, 학년은 3~6만 쓴다. 국어·미술·음악·체육·도덕·실과 등과 1~2학년은 버린다(1·2학년은 검·인정 교과서가 없다는 공지가 있다).
- `publisher`는 출판사 이름만 쓴다. 괄호 안(`천재교육(함순애)` → `천재교육`), 저자 이름, `출판사`·`㈜` 같은 꼬리는 뺀다. `수학 / 수학익힘 아이스크림미디어`처럼 적혀 있으면 과목은 수학, 출판사는 `아이스크림미디어`다(수학익힘은 과목이 아니다).
- 파일에는 여러 해의 게시물이 섞일 수 있다(게시물에 날짜가 없으니 첫 줄 제목으로 판단). 제목·글에 나오는 가장 최근 학년도를 따른다. 어느 게 최신인지, 또는 과목·학년의 글이 모호하거나 읽을 수 없거나 짐작해야 하면 `"certain": false`로 쓰거나 그 항목을 뺀다.
- 출판사 이름이 비었거나 20자를 넘으면 DB가 그 항목을 거부하니, 그런 항목(문장이나 출판사 나열 등)은 쓰지 말고 `certain: false`로 둔다.
- 글에 출판사가 명시된 것만 쓴다. 일반적으로 많이 쓰는 출판사 같은 기억·상식으로 채우지 않는다.
- 학년별로 출판사가 다르게 적혀 있으면 (학년, 과목)마다 항목 하나씩 쓴다.
- 글이 잘렸을 수 있다. hwp는 본문 전체를 읽지만 배포용 암호화 문서처럼 읽지 못하면 앞부분 미리보기만 남아 표가 중간에 끊길 수 있으니, 모자란 부분은 `certain: false`로 쓰거나 빼고 짐작하지 않는다.

## 진도 단계 (학교 평가계획 → 예상 진도)
12. `python -m eduapp_batch.run_progress` — 자녀가 있는 학교 중 평가계획을 아직 안 읽었거나 30일이 지난 학교(최대 20개)의 공지에서 학년·학기별 학생평가계획을 찾아, 과목·성취기준 코드·단원명·평가 월을 코드로 읽어 DB에 저장한다. 이 단계는 Claude 판단이 필요 없고 `work/`도 쓰지 않는다.
13. 마지막 줄 JSON을 확인한다(`{"<neis_code>": 값}`; 전체 실패면 `{"error": ...}`). 숫자 = 저장한 진도 행 수. 문자열 = 사유: `홈페이지 주소 없음`·`지원하지 않는 홈페이지`·`평가계획 공지 없음`·`첨부에서 글자를 읽지 못함`·`평가계획 형식을 읽지 못함`은 읽을 게 없다는 뜻이라 30일 뒤에 다시 보고, 그 밖의 `예외이름: 메시지`는 실패라 다음 실행에서 바로 다시 시도한다. 월을 못 찾아 버린 행이나 DB가 거부한 행이 있으면 `collect_runs`에만 남는다.
14. 같은 학교가 반복해서 `평가계획 형식을 읽지 못함`이거나 실패하면 사람이 확인해야 한다고 요약에 적는다(표 형식이 다른 학교일 수 있다). 코드는 고치지 않는다. 저장된 진도는 앱에서 "예상 진도"(평가 월 기준)로만 보인다.
15. 학교별 진도 결과를 한 문단으로 요약하고 끝낸다.

## 하지 않는 것
- DB 테이블 구조 변경, 데이터 삭제
- 저장소에 커밋·푸시
- `work/` 안에서 `answer.json` 쓰기 외의 수정 (`text_*.txt`·`meta.json`을 고치거나 지우지 않는다)
